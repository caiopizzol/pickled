## Install

Pickled runs on Bun. Use `bunx` for one-off runs, or install the CLI globally:

```bash
bunx @pickled-dev/cli init
```

This writes a starter `pickled.yml` in the current directory.

## The smallest config

A config needs a `product`, at least one `agent`, one named `access` path, and one `task`. An answer task (the default) carries at least one check.

```yaml
product:
  name: my-product
  description: short one-liner about what your product does

sources:
  readme: ./README.md

agents:
  quick:
    provider: claude-code
    model: claude-haiku-4-5

access:
  given_readme: { source: readme, tools: none }

tasks:
  - id: install
    prompt: How do I install my-product?
    agents: [quick]
    access: [given_readme]
    checks:
      mustMention: ["bunx my-product"]

threshold: 80
```

`threshold` is optional. Set it to make the run pass or fail on the overall score; omit it to see the score with no verdict.

## Preview the run

`--plan` walks the expansion and prints the cells without calling any model:

```bash
bunx @pickled-dev/cli check . --plan
```

## Run a check

```bash
bunx @pickled-dev/cli check .
```

Pickled spawns the agent, injects the registered source, asks the question, and checks the answer:

```
Task: install
  ✓ Well grounded (100%)

Overall: 100 / 100 · threshold 80 · run passes
Every answer met its checks.
```

## Compare context paths

The point of pickled is the comparison. Add a no-context path and run the same task down both:

```yaml
access:
  memory: { source: none, tools: none } # model memory only
  given_readme: { source: readme, tools: none } # your README injected

tasks:
  - id: install
    prompt: How do I install my-product?
    agents: [quick]
    access: [memory, given_readme]
    checks:
      mustMention: ["bunx my-product"]
```

Now `pickled check .` runs two cells. If `memory` fails and `given_readme` passes, your README is doing the work. If `memory` already passes, the model knew it without your docs. If `given_readme` fails, the answer is not in the source you registered: fix the context.

## Reach the live site with tools

Add a `web` access path to make the agent discover the answer instead of reading injected content:

```yaml
access:
  web_open: { source: none, tools: web }
```

A `web` (or `mcp`) cell that answers without invoking a tool is vetoed to `NO`: model memory does not count as evidence for a tool path.

## Score example answers offline

`pickled test` scores `examples.pass` / `examples.fail` strings against a task's checks with zero model calls, so you can catch brittle checks before a paid run:

```bash
bunx @pickled-dev/cli test .
```

## Build tasks

The checks above score an agent's *answer*. A build task instead has the agent *do the work*: it edits a throwaway workspace, and you score the result with `verify` commands. Set `kind: build`, declare a `workspace` and `verify`, and run it with `pickled build`:

```yaml
tasks:
  - id: add-endpoint
    kind: build
    prompt: Add a health-check endpoint using my-product.
    agents: [quick]
    access: [given_readme]
    trials: 3
    workspace:
      path: ./fixtures/app
      setup: [bun install]
    verify: [bun test]
```

Each `(agent × access)` cell runs `trials` times in a fresh workspace; the result is `k/n`. Build tasks run on edit-capable CLI agents (`claude-code`, `codex-cli`) and forbid `checks`/`examples` (their contract is `verify`). See the [pickled.yml reference](/pickled-yml) for the full build contract.
