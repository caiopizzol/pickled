Your code has a gate. A test breaks, the build goes red, the PR does not merge. That gate is why you trust your codebase to change without rotting.

The surface your agents read has no such gate. Your `AGENTS.md`, your `llms.txt`, your docs, your comments: they change every week, and nothing checks whether an agent still answers correctly afterward. The first signal that one drifted is a user watching an agent confidently get your product wrong.

That is a gap you can close with the CI you already run.

## Make agent understanding a check, not a hope

The move is the same one you made for code: run the check on every change, and fail the build when it regresses. With a deterministic eval (citations by code, traps by regex, expected substrings, no model judging another), the score is reproducible, so it is safe to gate on. A flaky score makes a useless gate. A contract score makes a real one.

Two tiers keep it fast and cheap:

```yaml
name: pickled

on:
  pull_request:

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: oven-sh/setup-bun@v2
      - run: bun install
      - run: bunx @pickled-dev/cli audit . --fail-on error

  check:
    needs: audit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: oven-sh/setup-bun@v2
      - run: bun install
      - run: bunx @pickled-dev/cli check .
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

The `audit` job runs no model calls. It is a cheap pre-flight that catches structural problems and registered-source or trap mismatches, and it fails fast before you spend a single token. Only if it passes does the `check` job run your scenarios against a real agent. Set a `threshold` in `pickled.yml` and the run passes or fails on the overall score.

That is the whole gate. A PR that weakens your `AGENTS.md` or breaks an answer your `llms.txt` is supposed to give now goes red, in the PR, before it ships.

## What changes when it is a gate

Stale prompt surface is product debt, and debt you cannot see is the dangerous kind. A CI gate turns an invisible, slow rot into a loud, immediate failure attached to the exact change that caused it. You stop finding out from users.

It also changes how the team treats those files. A `CLAUDE.md` with a test is no longer a document someone updates when they remember. It is a contract with a consequence. People keep it current because the build makes them.

And because the audit tier is free and the check tier is bounded by your matrix, you can afford to run it on every pull request, not as an occasional manual sweep. The point of a gate is that nothing gets past it.

## Try it

Add the two jobs above, set a `threshold`, and open a PR that intentionally breaks one answer. Watch it go red.
