You wrote an `AGENTS.md`. Maybe a `CLAUDE.md` too. You listed the package manager, the test command, the directories not to touch, the patterns you never want to see again. Then you trusted it.

Here is the uncomfortable question: do you know it works? Not "did the agent read it once." Does it still steer the agent today, after six months of edits, three new conventions, and one renamed directory?

For most teams the honest answer is no. The file is prompt surface, and prompt surface has no tests.

## Stale prompt surface is product debt

Your code has tests. When a function drifts from its contract, something goes red. Your agent instructions have nothing. An `AGENTS.md` can rot for months and the only signal is an agent quietly doing the wrong thing: running `npm` in a Bun repo, editing a generated file, reintroducing the exact pattern you wrote a line to forbid.

A stale instruction is worse than a missing one. A missing instruction leaves the agent to its priors. A stale instruction is a confident, wrong answer the next agent follows. It reads as policy.

The reason this debt is invisible is simple. Nobody runs the file. You write it for an agent, and then you never ask the agent whether it landed.

## Testing it means asking, then checking by contract

Put the file under test the way you would put an API under test: send the input, assert on the output.

The input is a question your `AGENTS.md` is supposed to answer. The output is what the agent says when that file is the only context it has. Then you check two things, both deterministically:

- Did the answer include the exact terms the instruction requires?
- Did the answer avoid the old or wrong terms that would send an agent down the wrong path?

No model grades another model. The score is the score.

## What that looks like

Register `AGENTS.md` as a source, ask the question it should answer, and pin the contract:

```yaml
product:
  name: my-repo
  description: the repo your agents work in

sources:
  agents_md: ./AGENTS.md

agents:
  local:
    provider: claude-code
    model: claude-haiku-4-5

access:
  injected: { source: agents_md, tools: none }

questions:
  - id: package-manager
    ask: What package manager does this repo use, and what installs dependencies?
    agents: [local]
    access: [injected]
    checks:
      mustMention: ["bun install"]
      mustNotMention: ["npm install", "yarn add"]

threshold: 100
```

In this controlled cell, `AGENTS.md` is the only registered source content pickled injects. `mustMention` asserts the answer you want. `mustNotMention` catches the stale-but-plausible answer you do not, the `npm` or `yarn` a thin or outdated instruction file lets through. Run it and you get a number per question, and a run that passes or fails against the threshold you set.

Now your `AGENTS.md` has a test. When someone switches the repo to a different package manager and forgets to update the file, the question goes red. The instruction is no longer something you hope is true. It is something you check.

## Put it in CI

The point is not to run this once and feel reassured. It is to run it on every change to the files that steer your agents, the same way you run your unit tests. Wire it into your pipeline and a drifting `AGENTS.md` fails the build before it ships, instead of surfacing as a confused agent three weeks later.

This is the internal case for testing agent legibility: not whether the outside world's agents understand your published product, but whether your own steering files still steer your own agents. Both are the same machinery. Both come down to the same idea: agent legibility is not a checkbox you tick when you write the file. It is behavior under test.
